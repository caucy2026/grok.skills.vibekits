# Linux 系统资源、加载与响应验收

适用于用户要求的VibeKits Linux性能优化。沿项目既定G6空闲CPU门禁，且将loading、操作反馈和实际完成延迟作为同等重要的验收项，不用“能启动”代替可用。

## 场景与指标

绑定commit、最终包SHA、实际PID/出生时间/ELF、系统/CPU/RAM/图形后端、屏幕和数据夹具。分开记录冷启动、热启动、稳定空闲、页面切换、真实推理开始/停止、头像动态/静止/离屏、应用中心加载/刷新/下载、任务完成后的回收。网络场景拆分本机排队/绘制与服务器/下载耗时；缓存命中与未命中分别报告。

- 整机：CPU、load1/5/15、逻辑CPU数、可用内存/swap、memory与IO压力、磁盘IO。load不是CPU百分比，多任务负载不能全部归因于VibeKits。
- App：GUI、relay、Node、WebKit及实际子进程完整家族单核等效CPU、RSS/PSS（可用时）、线程/FD/进程数、退出子进程CPU。不能只采主PID；无法完整计数标unknown。
- 响应：输入→首次可见反馈、输入→目标状态完成、冷/热启动首屏与可操作、帧耗时/卡顿/最长停顿。用单调时钟及真实目标端状态确认，工具“已接受/点击成功”不是完成。记录失败/超时/无响应，不能剔除后只统计成功样本。
- 每个交互场景至少20次有界重复，报告样本数、p50/p95/max及失败率；严格空闲沿既定至少300秒/61点场景，并记预热及采样污染。负载/资源采集不得引入忙等或持续截屏。

## 判定

硬门禁沿原约定：严格空闲完整家族单核CPU中位≤5%，不能按核心数折算或豁免历史失败。新增响应工程目标：本地按钮首次反馈p95≤100ms，本地页面切换完成p95≤300ms；尚无可靠测量时标未验证，不声称通过。外部网络/模型/大型文件任务不要求300ms完成，但应及时给出真实进度、可取消且不阻塞本地交互。不随意改变系统性能/电源/图形策略来制造通过。

内存/FD/线程/进程需在固定循环后回落，无持续增长、OOM或失控后台进程；绝对预算依据真实硬件与产品功能记录，不凭空承诺固定值。帧率、启动与loading先建立同机基线并记录改进目标，不能将工程目标冒充已达结果。

## 优化与详细报告

先定位占用/延迟到模块、线程或实际调用，保留失败证据，添加能检出原问题的正/负回归，再做最小修复。优先取消重复/无效工作、限制重绘、事件驱动更新与正确生命周期释放，不关闭原功能、不放宽新鲜度/权限/超时来换数字。优化后重建并绑定新SHA，同机同输入复验资源及功能；没有对照不可给“提升百分比”。

报告必须包含：环境与候选；场景/样本/原始证据索引；优化前后各指标表；根因证据及未证实假设；精确源码变化；回归/负控/真实UI结果；整机与App归因边界；采集工具开销及污染；副作用和恢复；未达标项及下一动作。阶段报告可先给，但明确未完成，不把文档更新当作性能优化完成。临时原始采样按24小时、错误证据按7天上限清理；脱敏正式汇总和索引保留，不记录正文/Key。
